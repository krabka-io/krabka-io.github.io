# Contribute to the Krabka website

This repository maintains krabka.io and its website tools. Keep issues and pull
requests focused on one change that a reviewer can check in one sitting.

Read [AGENTS.md](AGENTS.md) and the
[website style guide](docs/style_guides/website_style_guide.md) before changing
copy, content structure, or presentation. The website guide's explicit website
overrides take precedence over the linked broker prose guide.

## Choose the source repository

Edit website pages, layouts, and tools here. Documentation under
src/content/docs/ is generated by scripts/sync-docs.mjs and is not committed.
Edit those guides in their component repository, then sync them for local
verification. Do not submit generated copies as website source changes.

Before substantial work, check existing issues and explain the intended change
in a focused issue. Include the affected page or component, the current result,
and the expected result. Use the private route in
[SECURITY.md](SECURITY.md) for sensitive vulnerability reports.

## Prepare a local checkout

Use Node.js 22.12.0 or later, npm, Git, and Git LFS. CI uses Node.js 24. The sync commands
read sibling repositories or clone missing ones from GitHub; network access is
needed for missing source inputs. Release-tag lookup uses the GitHub API; authenticated gh is useful for that lookup.

Read [the development instructions](docs/development.md) for dependency
installation, input preparation, and local preview. A pages-only build does
not compile the browser tools. It still needs the synced and generated inputs
that its pages import. Do not treat missing tool binaries as a working tool.

Use npm run build:site for the pages-only build. The full npm run build also
compiles WebAssembly tools and syncs documentation and proofs. Optional tool
builds have further Rust, WASM, Docker, or other prerequisites; use the
subsystem instructions linked from the development guide. A copy edit does
not require every optional integration suite or toolchain.

## Verify and submit a change

Prepare the required inputs, then run the existing pre-PR checks:

```sh
npm run build:site
npm run test:website
npm run check-links
npm run check-seo
```

Read [the testing guide](docs/testing.md) for check prerequisites, additional
checks selected by the change, and the limits of local verification. Check
repository-relative Markdown links separately from the built-site link check.

Preserve the evidence scope of claims, source-generated benchmark numbers,
CI-covered code samples, and upstream documentation ownership. Check
presentation changes in light and dark themes at phone width (375 px) and
desktop width; browser tools intentionally stay dark.

In the pull request, state what changed, why it changed, which checks ran, and
anything that could not be tested. Include actual captures for a visual change
when they help review it. A local check does not verify a deployment. Do not
change deployment settings or publish as part of an unrelated documentation
change.
